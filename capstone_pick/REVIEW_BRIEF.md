# 외부 검수 요청: SO-101 픽앤플레이스 + 모방학습 데이터 파이프라인

이 문서는 다른 AI 모델에게 코드 검수를 요청하기 위한 배경 설명입니다. 함께 보내는 소스와 이 문서를 읽고, 아래 "검수 요청 사항"에 답해 주십시오.

---

## 1. 시스템 개요

**과제**: Gazebo Harmonic + ROS 2 Jazzy 시뮬레이션에서 모바일 매니퓰레이터(JD-AMR cube 차동구동 베이스 + SO-101 5축 팔 + 그리퍼)가 3cm 큐브를 자율로 집어 옮깁니다.

**두 갈래로 진행 중**:
1. **규칙 기반 파이프라인** (완성) — YOLO 검출 → RGB-D 역투영 → 주행 폐루프 접근 → 손목캠 비주얼 서보잉 → 파지 → 운반. 실좌표 판정 게이트 6/6 통과.
2. **모방학습** (진행 중) — 규칙 기반을 시연자로 삼아 데이터를 모으고 ACT(Action Chunking Transformer) 정책을 학습. **두 번 학습했고 두 번 다 평가 0/10 실패.**

**하드웨어 제약**: RTX 5050 Laptop (VRAM 8GB), 16코어 CPU. Nav2·MoveIt 미사용(팔 5축 자유도 제약으로 계획기 대신 고정 자세 + 파지 포켓 방식).

**판정 원칙**: 이 프로젝트는 처음부터 "로그가 아니라 시뮬레이터가 보고하는 물체 실좌표로 판정한다"를 지켜 왔습니다. `gz model -m <name> -p`로 큐브 위치를 직접 조회해 들림·이동을 확인합니다.

## 2. 지금까지 겪은 주요 결함 (검수 시 참고)

이 코드베이스는 다음 함정들을 실측으로 하나씩 발견해 고쳐 온 결과물입니다. **비슷한 종류가 더 남아 있는지 봐 주십시오.**

| # | 증상 | 진짜 원인 | 대응 |
|---|---|---|---|
| 1 | 팔 궤적이 스냅으로 실행되거나 무시됨 | 강의실 LAN의 다른 머신과 DDS 토픽(`/clock`)이 섞여 시간이 널뜀 | `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` |
| 2 | 파지 시 앞바퀴가 들려 구동륜 접지 상실 | 파지 자세에서 손끝이 바닥을 눌러 지렛대 작용 | 자세 lift 1.20→1.15, 차체 밸러스트 3→15kg |
| 3 | "성공"인데 물체가 그리퍼에 꽂혀 있음 | 위치 제어가 물체 두께 너머로 명령해 **손가락이 물체를 관통** | 닫힘 명령 클램프(−0.035) + 스톨각 판정 |
| 4 | 수집 데이터가 에피소드 앞 1.3~3.8초만 존재 | 수집 루프에서 이미지를 디코드하느라 ROS 콜백이 굶어 **sim 클록 자체가 느려짐**(wall 60초에 sim 1.6초) | 루프는 원시 메시지만 저장, 디코드는 저장 단계로 |
| 5 | 병렬 수집 시 한 워커가 전 에피소드 1프레임 | 그 워커가 `/clock`을 못 받아 `use_sim_time` 시간이 0에 고정 | 노드 시작 시 클록 수신 대기 + 프레임 수 검증 |
| 6 | 학습 loss는 낮은데 평가 0/10 | `action[t] = state[t+1]`이 20Hz에서 차이 0.003rad — **"가만히 있기"가 최적해** | (미해결, 아래 검수 요청 사항) |

**공통 패턴**: 관측 지표(로그·loss)가 물리적 사실과 어긋나는 사고가 반복됐습니다.

## 4. 핵심 설계 결정과 그 근거

검수 시 이 결정들이 타당한지도 봐 주십시오.

**(a) 주행을 제거하고 팔만 쓰는 데이터로 전환**
주행 접근을 포함하면 데이터의 61%가 "팔은 정지, 바퀴만 굴러가는" 프레임인데, `action`에는 주행 명령(`cmd_vel`)이 없어 정책이 그 구간을 재현할 수 없습니다(평가에서 배회한 원인). 그래서 물체를 팔 작업 반경(포켓 0.355~0.405m) 안에 바로 스폰하고 `skip_approach` 모드로 실행합니다.

**(b) 관측은 로봇 탑재 카메라만**
전방 RGB-D(66° FOV) + 손목캠(87° FOV). 외부 고정 카메라를 쓰지 않는 이유는 실물 이식 가능성입니다. 손목캠은 실물 SO-101 공식 마운트인 RealSense D405(87°)에 맞췄습니다 — 이전 60°에서는 파지 직전 3cm 큐브가 화면의 52%를 차지해 중심 추정이 무너졌습니다.

**(c) 물리 스텝 1ms 고정**
4ms·8ms를 시도하면 RTF가 1.6·4.8배로 오르지만 **접촉이 발산해 물체가 1~1.9m 튕겨나갑니다**. gz-sim 물리는 단일 스레드라 인스턴스 하나의 RTF 상한이 1.0이고, 그래서 배속 대신 **병렬 인스턴스**로 처리량을 얻습니다.

**(d) 파지 성립 판정은 그리퍼 관절각 구간으로**
`GRIP_HOLD_MIN=0.05 < angle < GRIP_HOLD_MAX=0.30`. 하한만 두면 아예 닫히지 않은 상태가 새어 나가고, 명령 대비 잔여각으로 보면 유지용 재조임 때 0이 되어 오판합니다. 관통은 −0.1 아래로 내려가 이 구간 밖입니다.

**(e) 낙하 판정은 손목캠 블롭 면적 + 상대운동**
그리퍼 각도로는 낙하를 볼 수 없습니다(유지 목표를 명령해 두면 물체가 빠져도 각도가 남음). 손목캠 면적이 임계 아래일 때, 정지 화면만으로는 "죠 안에서 밀린 상태"와 "낙하"가 구분되지 않아(실측: 면적·중심이 완전히 동일) **10cm 후진 후 블롭 중심 이동량**으로 가릅니다(쥔 상태 9~75px vs 낙하 217~249px).

## 5. 검수 요청 사항

### 우선순위 1 — 모방학습이 실패하는 이유

두 번의 학습이 모두 평가 0/10이었습니다. 두 번째는 원인을 `action` 정의로 특정했지만(위 표 #6), **정말 그것뿐인지, 다른 결함이 겹쳐 있는지** 판단해 주십시오. 구체적으로:

1. `rule_collect.py`의 관측·행동 기록 방식(`action[t] = state[t+1]`)이 ACT 학습에 적합한가? 대안(미래 상태 `state[t+k]`, 실제 명령 구독, 델타 액션 등) 중 무엇이 이 구성에 맞는가?
2. `act_eval.py`의 추론 루프가 정책을 올바르게 구동하는가? (정규화, `select_action` 사용법, chunk 소비, 제어 주기)
3. 데이터 규모(19편 ~13,000프레임)와 학습 설정(20K 스텝, batch 8, chunk 100)이 균형이 맞는가?
4. 관측 구성(전방 RGB-D + 손목캠, 640×480)에 학습을 방해할 요소가 있는가?

### 우선순위 2 — 숨은 결함

위 §2의 사고 6건과 **같은 종류의 함정이 코드에 더 있는지** 봐 주십시오. 특히:

- 시간 처리 (`use_sim_time`, wall clock 혼용, 타임아웃)
- 비동기 처리 (액션 서버 응답 대기, gz 서비스 호출, 프로세스 종료)
- 조용한 실패 (예외를 삼키거나, 실패를 성공으로 보고하거나, 종료 코드를 버리는 곳)
- 병렬 실행 시 자원 충돌 (`parallel_collect.sh`)

### 우선순위 3 — 구조·품질

- `pick_node.py` 1,685줄이 단일 파일입니다. 분리한다면 어떤 경계가 자연스러운가?
- 실측 상수(캘리브레이션 값)와 로직이 섞여 있는데, 설정 분리가 유익한가 아니면 현재 방식(주석에 근거를 붙여 코드 옆에 두기)이 나은가?
- 테스트 가능성 — 지금은 실좌표 게이트 스크립트가 유일한 검증 수단입니다
