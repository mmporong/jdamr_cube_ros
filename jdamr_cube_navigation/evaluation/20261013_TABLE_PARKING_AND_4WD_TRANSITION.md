# 책상 정밀주차와 4륜 전환 기록 — 2026-10-13

## 1. 현재 결론과 적용 범위

- 후면 볼캐스터를 같은 서보·바퀴로 교체해 **4륜 결합을 완료**했다. 전좌 ID2·전우 ID1·후좌 ID3·후우 ID4이며, 네 서보의 회전과 바닥 수동 주행을 운영자가 확인했다.
- 4륜 펌웨어를 Pi/ESP32에 반영했다. 같은 측 앞뒤 명령은 SYNCWRITE 한 패킷으로 보내고, 네 엔코더를 개별 언랩한 뒤 좌우 평균을 기존 v2 프로토콜로 보낸다. 호스트 드라이버와 기준점은 유지했다. 실제 후륜축·전체 외곽 측정과 URDF 갱신은 완료하지 않았다.
- 4륜 책상 **3cm 목표는 양쪽 약 3.5cm**로 보고됐다. **1cm 목표의 최종 남은 간격은 15mm**이며 좌우별 값은 최종 보고에서 나누지 않았다. 1cm 달성이나 반복 성공으로 집계하지 않는다.
- 제어 후진 45.6cm·회전 8.1475°·재접근을 수행했다. 수치는 바퀴 odom 기록이며 외부 이동량·각도 실측과 구분한다. 운영자가 들어서 옮기면 odom이 따라오지 않았으므로 다음 반복은 제어 후진·회전으로 잇는다.
- 사용자의 퇴근·주행 중지 요청 뒤 비상정지 `engaged`와 모든 주행·카메라 서비스 `inactive`를 확인했다. 마지막 위치는 책상 앞이며 HOME을 변경하지 않았다.
- 아래 2~6절은 **4륜 적용 전 2륜 기준선·설계 분석**을 보존한 기록이다. 저녁의 실차 결과와 다음 실행 상태는 7~8절을 우선한다.

## 2. 4륜 적용 전의 2륜 기준선과 남은 문제

### 하드웨어·운영

- 상하 차체를 결합하고 높였다. LiDAR 물리 장착 위치는 유지했고, 기둥 자기 반사는 기존 스캔 필터 설정으로 처리했다.
- 카메라는 상판 맨 뒤, 약 1m 높이에서 아래를 본다. 앞끝–렌즈 수평 거리 340mm는 사용자 확인값이다. 현재 설정의 pitch 15°는 사용자 근사값, yaw 약 1.25°는 근거리 두 자세에 맞춘 잠정값이며 독립 외부 보정이 아니다. 높이 설정 0.907054m도 과거 바닥 후보 평면으로 산출한 값이다.
- 전면 하중 부족으로 바퀴가 떴다는 사용자 보고가 있었고 전면 추를 추가한 뒤 개선됐다고 보고했다. 접지력이 모든 동작에서 같아졌는지는 별도 측정하지 않았다.
- 접촉센서는 5V·GND만 연결됐다. 신호 입력이 없어 눌림 검출과 후면 접촉 0cm 도킹은 구현·검증되지 않았다.
- 복귀점 명칭은 **도크**다. 운영자가 등록한 HOME을 사용하며 주행 도중 현재 위치를 HOME으로 덮어쓰지 않는다.
- USB 재연결 문제, 전원 차단, 지도/파라미터 응답 지연, PC 표시 부하는 구동 기울어짐과 별개 항목이다. 모든 실패를 배터리 또는 대시보드 하나의 원인으로 묶지 않는다.

## 3. 4륜 전환의 적합성

**조건부로 진행할 만하다.** 후면도 구동하면 전면 구동륜에만 견인·제동을 맡기는 부담을 줄일 수 있다. 그러나 기존에도 전면 2륜과 후면 볼캐스터 2개로 지지했으므로, 단순히 지지점 개수가 늘어 안정해지는 것은 아니다. 핵심 변화는 후면 지지점도 구동륜이 된다는 점이다.

| 항목 | 기대할 수 있는 점 | 조립·제어 조건 |
|---|---|---|
| 하중·접지 | 전면이 가벼운 상태에서 후면도 추진·제동에 참여 | 네 바퀴 높이와 접지 하중을 맞출 것. 강체 4점은 바닥/조립 오차로 한쪽이 다시 뜰 수 있음 |
| 직진 | 같은 측 앞뒤 바퀴가 추진력을 나눔 | 동일 타이어·유효 반경, 평행한 축, 개별 방향·속도 설정 필요 |
| 회전 | 기존 좌우 차동 명령 개념 유지 가능 | 고정 4륜은 회전에 횡미끄럼이 필요해 회전 저항·유효 트레드가 달라짐 |
| 정밀 주차 | 접지 조건이 개선되면 반복성 향상 가능 | 엔코더 외 방향 관측, 저속 제동, 카메라 보정을 함께 해결해야 함 |
| 전력 | 부하가 나뉘어 개별 모터 부담 감소 가능 | 총 소비전력이 줄거나 두 배라고 단정할 수 없음. 제자리 회전의 전류 증가 확인 필요 |

스키드 조향에서 미끄럼 때문에 순수 구름 차동구동 모델만으로 실제 회전을 정확히 예측할 수 없다는 것은 [Mandow 등, IROS 2007 원논문](https://babel.isa.uma.es/_utils/downloads/logdownloads.php?f=downloads%2Fjafma%2Fpapers%2Fmandow2007ekw.pdf&t=pdf&u=jafma)의 관측과 일치한다. 접지 높이·축 평행도·좌우 하중을 먼저 맞추고, 바닥 편차에도 접지가 유지되지 않으면 작은 유연성 또는 축의 요동 구조를 고려한다. 바퀴 네 개를 강하게 고정하는 것만으로 접지 문제를 끝냈다고 판단하지 않는다.

### 현재 제원에서 예상할 배치 — 설계 계산, 실측 아님

현재 `new_base_geometry.yaml`과 `new_base_real.urdf`는 차체 길이 340mm, 폭 450mm, 좌우 바퀴 중심 간격 510mm, 앞끝에서 전륜축까지 65mm를 사용한다.

- 후륜축도 뒤끝에서 65mm 안쪽에 대칭 배치하면 전후 축간 거리는 **340-65-65=210mm**다.
- 기존 후면 캐스터의 URDF x=-215mm는 실측이 아닌 모델 대용값이다. 이 값을 후륜 축 위치로 확정하지 않는다.
- 위 대칭 배치라면 축간/좌우폭 비는 약 **0.41**이다. 길고 좁은 배치에 비해 회전 중 바퀴 접점의 횡이동 요구가 작을 것으로 예상하지만, 실제 회전 저항이나 정밀도를 계산만으로 보증하지 않는다.
- 앞뒤 동일 측 바퀴는 같은 좌우 선(y=±255mm)에 두는 배치를 권장한다. 뒤 캐스터의 기존 y=±215mm 위치를 그대로 서보 축 중심으로 쓰면 앞뒤 트레드가 달라진다.
- 현재 차체 무게·무게중심·모터 장착 강성·실제 바닥 마찰을 모르므로 토크 여유와 전도 안정성의 정량 판정은 남아 있다.

### 전원은 조립 전에 확인

저장소는 STS3215 계열과 Waveshare General Driver for Robots를 사용한다. 제조사는 이 보드의 버스 서보 경로 장기 전류 상한을 **5A**로 안내한다. 주소를 많이 연결할 수 있다는 사양은 전력 용량을 뜻하지 않는다. [보드 공식 FAQ](https://www.waveshare.com/wiki/General_Driver_for_Robots)

공식 ST3215 12V 제품은 구속 전류 **2.7A**이므로 네 개의 단순 합은 **10.8A**다. 이는 정상 주행 소비전력 예측이 아니라 최악 부하 합산 예시다. 7.4V 계열 등 변형이 있으므로 실제 서보 라벨·배터리 전압·보드 리비전을 확인하기 전 공급 전압을 정하지 않는다. [서보 공식 사양](https://www.waveshare.com/wiki/ST3215_Servo), [전압별 제품](https://www.waveshare.com/product/modules/st3215-servo.htm)

회전 중 측정 전류와 전압 강하가 기존 전원 경로 용량을 넘으면, 적합한 별도 서보 전원 분배를 설계하고 통신 기준 GND를 공유한다. 전원 출력을 임의 병렬 연결하거나 보드 스위치 한도를 무시하는 방식은 채택하지 않는다. 과거 Pi 전원 차단의 원인이 배터리였다고 확정하는 내용은 아니다.

## 4. 소프트웨어 변경 경계

현재 모터 매핑은 오른쪽 ID1 / 왼쪽 ID2다. 명령과 피드백은 두 바퀴용이며 `/odom` 방향은 두 엔코더 차이로 계산한다. ROS의 일반적인 복수 휠 지원 여부와 별개로 이 저장소는 커스텀 펌웨어·드라이버를 수정해야 한다.

| 파일·계층 | 필요한 변경 |
|---|---|

ROS 2 Control Jazzy도 좌우 휠 이름 배열을 지원하지만, 이번 전환에 ros2_control 전체 교체를 필수로 추가할 필요는 없다. [공식 문서](https://control.ros.org/jazzy/doc/ros2_controllers/diff_drive_controller/doc/userdoc.html)

### 차체 기준점 변경을 빠뜨리지 않기

현재 `base_link/base_footprint` 원점은 전륜축 중심의 바닥 투영이다. 4륜 대칭 모델에서는 **전후 축의 중간**을 운동학 기준점으로 삼는 구성을 권장한다. 이는 실제 회전 중심이 항상 그 점이라는 뜻은 아니며, 미끄럼 때문에 유효 운동학 보정은 별도다. 앞축 원점을 유지하는 설계도 가능하지만 회전할 때 그 지점의 횡속도를 포함한 오프셋 변환을 처리해야 한다.

축간 210mm 가정이면 새 원점은 현재 원점보다 105mm 뒤다. 물리 장착을 그대로 둔 좌표 변환 예시는 아래와 같다.

| 항목 | 현재 x | 새 기준 x |
|---|---:|---:|
| 전륜축 | 0mm | +105mm |
| 후륜축(설계안) | -210mm | -105mm |
| 차체 앞끝 | +65mm | +170mm |
| LiDAR | -10mm | +95mm |
| 카메라 렌즈 | -275mm | -170mm |

이 경우 주차의 front extent를 65mm로 남겨 두면 105mm의 기준점 오류가 생긴다. 앞끝–렌즈 수평 거리 340mm는 물리 장착이 같으면 유지된다. 실제 조립 후 실측값으로 계산하고, 가정값을 운영 YAML에 선반영하지 않는다. 환경 지도가 그대로면 새 지도 작성부터 다시 할 필요는 없지만 TF 변경 후 위치초기화와 도크/목표 기준점을 확인해야 한다.

## 5. 권장 진행 순서와 각 단계의 완료 기준

1. **2륜 상태 동결·기록** — 마지막 23/8mm 결과, bag, IMU 비교와 코드 `5c0f424`를 기준선으로 보존한다. 현재 2륜 설정을 4륜 장착 후 그대로 주행시키지 않는다.
2. **조립 치수·전원 결정** — 실제 서보 전압형, 배터리/보드/배선 용량, 후륜 축간 거리, 네 바퀴 지름·높이를 정한다. 앞뒤 같은 측 축을 평행하게 맞추고 실제 하중 상태에서 네 바퀴 접지를 확인한다.
3. **고유 ID·회전 방향 확인** — 새 서보는 개별 연결로 ID 중복을 없앤다. 예를 들어 기존 1/2를 유지하고 후륜 3/4를 쓰되 실제 등록 후 확정한다. 바퀴를 띄운 상태에서 각 휠의 전진 명령과 엔코더 증가 부호를 확인한다. 이 단계의 구동은 조립 완료 후 사용자 실행 요청 때 수행한다.
4. **펌웨어·드라이버를 함께 전환** — 네 바퀴 명령/피드백/정지, 새 프레임 버전, 네 모터 통신 시간을 검증한다. 현재 20ms 상태 주기 가정이 실제로 유지되는지 확인하고 지연 시 실제 시간 정보를 사용한다. 새 firmware와 대응 driver를 한 묶음으로 배포한다.
5. **좌표·외곽·센서 갱신** — 축 중앙 기준 URDF/TF, 앞뒤 extent, footprint, 카메라 보정을 실측과 일치시킨다. 기존 바닥 지도는 먼저 재사용하고 위치초기화한다.
6. **짧은 바닥 주행으로 운동학·방향 관측 정리** — 같은 실제 하중에서 짧은 직진·후진과 양방향 회전을 수행해 휠 반경/유효 트레드를 맞춘다. 네 엔코더와 IMU를 같이 보고, 바퀴 odom과 융합 방향을 분리 기록한다. EKF 활성 시 드라이버의 중복 TF 발행을 끈다. 절대 자기방위는 모터 주변 간섭 확인 없이 사용하지 않는다.
7. **미세 제동을 먼저 맞춘 뒤 5cm → 3cm → 1cm** — 책상 밖에서 작은 전진 명령의 실제 정지 거리를 확인한다. 책상에서는 경계가 보이는 위치에서 정렬·재측정하고, 짧은 마지막 구간을 융합 방향으로 유지한다. 각 거리에서 좌우 실측과 실제 회전 여부를 확인한 뒤 줄인다. 이는 전환 시 한 번 하는 조정 순서이며 매 출발마다 반복하는 준비 절차가 아니다.

초기 1cm 목표는 현재 소프트웨어의 양쪽 10±3mm 조건을 임시 기준으로 삼고 사용자 실측으로 평가한다. 좌우 간격 차이가 3mm라면 폭 450mm에서 약 0.38°에 해당하므로, 방향 반복성 목표는 대략 0.3~0.4° 수준이 적절하다. 이는 새 설계의 목표치이며 달성 성능이 아니다.

카메라의 최종 경계가 계속 사라지면 4륜과 별개로 시야·pitch/roll/yaw 보정 또는 관측 가능한 책상 옆면 사용을 해결해야 한다. 관측 소실을 성공으로 바꾸거나 임의 거리 보정을 누적해 1cm를 주장하지 않는다. 접촉센서를 이용한 후면 0cm 도킹은 신호선·입력 검증 뒤 별도 단계로 둔다.

## 6. 아직 확정하지 않은 값

- 추가 서보의 정확한 전압형·ID·방향, 전원 계통의 실제 부하 여유.
- 실제 후륜 축간 거리·접지 높이·하중 분배, 전체 무게와 돌출 외곽.
- 새 하중에서 휠별 유효 반경, 회전용 유효 트레드, 미세 접근 정지 거리.
- 카메라의 정확한 외부 보정 및 최종 1cm에서 사용할 수 있는 관측 범위.
- IMU 기반 방향 추정의 bias/축 검증과 실제 4륜 반복 주차 성능.

AMCL Axis B 기존 5건 처리, 포트폴리오·외부 발행, 후면 접촉 도킹 구현은 이번 분석으로 자동 승인하거나 변경하지 않는다.

### 정지 중 소프트웨어 수정

- 1cm 책상 마지막 구간은 기본 Parking 옵션에서도 기존 정밀 odom 직선 기능을 사용한다. RPP의1cm XY goal tolerance로 미세 전진이 먼저 끝나는 경로를 피한다.
- 경계가 보이는 단계에서 면을 관측/정렬하고 마지막 짧은 구간에서는 미세 회전을 반복하지 않는다. 유효한 면을 odom에 고정해 이동량·정지 후 간격·후속 보정을 같은 기준으로 계산한다.
- 동결 면으로 내부 접근을 확인한 뒤에도 그 면과 법선을 odom 기준으로 보존한다. 후진 이탈 거리와 정지 후 clearance는 같은 면으로 판정하고, Nav2 경로만 현재 map pose로 변환해 AMCL 변화가 이탈 성공을 바꾸지 않게 한다.
- 최종 경계가 안 보일 때는 새 관측을 만들어 넣지 않는다. 최신 깊이 프레임이 충분하고 거부 이유가 `no_table_edge_candidate`뿐인 경우에 한해 동결 면·odom·정지 확인으로 **내부 추정**을 기록한다. 오래된 영상, observer silence, 지연/통신/센서 실패는 이 대체 판정에 포함하지 않는다.
- 새 깊이 경계가 유효하면 이를 우선한다. 확인 근거는 `fresh_depth_table_edge` 또는 `frozen_table_edge_odom_stop`, 실물 상태는 `NOT_EXTERNALLY_MEASURED`로 남긴다. 동결면이 없는 새 시도에서 경계 없이 출발하는 기능을 추가한 것은 아니다.
- import 순서 lint 네 지점도 정리했다. 기존 AMCL Axis B5건은 사용자 선택 대기이므로 바꾸지 않는다. 검증 결과와 Pi 반영 상태는 아래 완료 기록을 따른다.
- 출발 요청 뒤 검토·검수·리뷰·전체 검사·추가 문서를 끼우지 않는 운영 규칙을 JD-AMR `AGENTS.md`와 양팔 저장소 `CLAUDE.md`에 맞췄다. 사용자 최종 간격을 임의 추가 여유로 늘리지 않는다. 기본 `go`에서 기록기·UDP/부하 진단을 자동 기동하지 않으며 `--record-diagnostics`로 선택한다. 센서·통신·충돌 정지와 실제 최종 정지 판정은 유지한다.
